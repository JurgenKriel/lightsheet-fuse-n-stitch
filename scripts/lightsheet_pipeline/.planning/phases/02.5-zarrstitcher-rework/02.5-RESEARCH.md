# Phase 2.5: ZarrStitcher Stitching Rework — Research

**Researched:** 2026-05-19
**Domain:** Globally-optimised mosaic tile stitching for lightsheet zarr data, 3D feather blending, weighted-LSQ position solvers
**Confidence:** HIGH (algorithm details verified from MATLAB source); MEDIUM (run-time behaviour on KL018 not yet measured)

## Summary

Phase 2 produced `fused_direct.zarr` with shape `(1, 2, 1557, 8585, 10095)`, but mid-volume planes still show visible tile seams and per-tile illumination ramps. The cause is in the stitching path of `07_direct_fuse.py` (not in `fuse_sides`, which is correct):

1. **Single-spanning-tree position propagation** — pairwise NCC shifts on a single mid-Z reference plane are propagated by BFS from tile 0 along an MST. Tiles far from tile 0 accumulate error.
2. **2-D cosine-taper accumulator** — per-tile separable cosine-taper weights are summed onto a float32 canvas and normalised by a weight canvas at the end. At 3- and 4-tile corner overlaps, the separable 2-D taper does NOT integrate to a constant, producing brightness ramps.
3. **Mid-Z-only quality** — tile pairs that are background at the chosen reference Z score NCC ≈ 0 and are excluded from the MST, even if they have rich content elsewhere in Z.

PetaKit5D's `ZarrStitcher` (Ruan et al., *Nature Methods* 2024) fixes (1) by solving a **weighted constrained linear least-squares problem** over the full pairwise constraint graph (MATLAB `lsqlin`), fixes (2) by **3-D feather blending** based on a distance-transform from the tile's interior region (so weight sums are always ≥ 1 and any number of overlapping tiles average correctly), and fixes (3) by running NCC on **3D regions with downsampling** (`normxcorr3_fast` + `max_pooling_3d`) or on multi-Z **MIP slabs** rather than a single plane.

There is no pure-Python port of PetaKit5D's stitcher. `PyPetaKit5D` is an MCR-backed wrapper that requires MATLAB Runtime — not viable on this HPC (MATLAB is not available and the install is large). The pragmatic recommendation is **multiview-stitcher** (BSD, pure Python, zarr-native, `dask`+`xarray`+`spatial_image` backend, optional CuPy acceleration in v0.1.49+). It implements exactly the two architectural changes we need: pairwise phase correlation + **global optimisation** (`registration.register(..., groupwise_resolution_method="global_optimization")`) and **`weighted_average_fusion`** with a `blending_widths` parameter that builds smooth blending weights at tile boundaries (`weights.get_blending_weights`).

**Primary recommendation:** Adopt `multiview-stitcher` (v0.1.52, May 2026) in a new `mvstitch_env` conda environment. Build a new `08_stitch.py` that (a) reads the existing dual-side-fused per-tile output (or re-runs `fuse_sides` per slab to avoid materialising 30 intermediate per-tile zarrs), (b) wraps each tile as a `spatial_image` with the stage-position metadata already in `tile_manifest_corrected.json`, (c) calls `registration.register()` with `pairwise_reg_func=phase_correlation_registration` and `groupwise_resolution_method="global_optimization"`, then (d) calls `fusion.fuse()` with `output_zarr_url=fused_direct.zarr` and `blending_widths` set to ~half the tile overlap (≈144 px). `fuse_sides` and friends remain untouched.

This is a **fallback-friendly plan**: if `multiview-stitcher` doesn't perform well on the 30-tile/1557-plane volume, the secondary recommendation is a hand-rolled pure-NumPy implementation of the two key algorithms (`lsqlin`-style weighted LSQ over translation constraints + bwdist-based 3D feather blending) — a clearly bounded port of ~500 LOC from the MATLAB source files identified below.


Key data-flow properties:
- Per-tile dual-side fusion (`fuse_sides`) is invoked from BOTH stages (same function, different callers). It is never modified — STITCH-06 compliant.
- Stage 1 writes a small JSON of 30 affine transforms (the only output that depends on the full 1557-plane volume's content is via the mid-Z reference slab used for NCC).
- Stage 2 array tasks share NO mutable state — same chunk-aligned partition pattern proven in Phase 2 (`02-RESEARCH.md` §Z-Range Partition Table).
- The fused canvas is held only one Z-slab at a time (~21 GB per process, identical to current Phase 2 footprint).

### Pattern 1: Pairwise + Global Registration via multiview-stitcher

```python
# Source: multiview-stitcher v0.1.52 registration.py + README example
# [CITED: github.com/multiview-stitcher/multiview-stitcher]
from multiview_stitcher import registration, msi_utils
from multiview_stitcher import spatial_image_utils as si_utils

# For each tile m=0..29, build a spatial_image with stage-position translation.
# `tile_data_3d` is the dual-side-fused (Z, Y, X) uint16 volume for that tile.
sims = []
for m in range(n_tiles):
    pos = tile_positions[m]   # from tile_manifest_corrected.json
    sim = si_utils.get_sim_from_array(
        tile_data_3d_for_m,     # ndarray (Z, Y, X) or dask array
        dims=("z", "y", "x"),
        scale={"z": 3.515, "y": 0.915, "x": 0.915},   # µm
        translation={"z": 0.0, "y": float(pos["y"]) * 0.915,
                     "x": float(pos["x"]) * 0.915},
        transform_key="stage_metadata",
    )
    sims.append(sim)
msims = [msi_utils.get_msim_from_sim(sim) for sim in sims]

# Pairwise + global registration in one call
params_dict = registration.register(
    msims,
    reg_channel_index=0,
    transform_key="stage_metadata",
    new_transform_key="registered",
    pairwise_reg_func=registration.phase_correlation_registration,
    groupwise_resolution_method="global_optimization",
    post_registration_do_quality_filter=True,
    post_registration_quality_threshold=0.2,   # mirrors current ncc_threshold=0.5 idea
    return_dict=True,
)
# params_dict["params"]: {msim_idx: affine_xarray} — the registered transforms
# params_dict["pairwise_registration_results"]: per-edge NCC, shift, success
# params_dict["groupwise_resolution_info"]: residuals, convergence
```

### Pattern 2: Weighted-Average Fusion with Blending Widths

```python
# Source: multiview-stitcher v0.1.52 fusion.py
# [CITED: github.com/multiview-stitcher/multiview-stitcher fusion.py]
from multiview_stitcher import fusion

# After registration, fuse the same sims using the new transform key.
# blending_widths spans the tile-overlap region (≈ overlap / 2 = 144 px for KL018).
# This is the multiview-stitcher equivalent of "feather blending" — weights ramp
# from 0 at the tile edge to 1 at the interior, summed across all overlapping tiles,
# then the canvas is divided by the weight sum (always > 0).
fused = fusion.fuse(
    sims=[msi_utils.get_sim_from_msim(m) for m in msims],
    transform_key="registered",
    fusion_func=fusion.weighted_average_fusion,   # default
    blending_widths={"z": 0, "y": 144, "x": 144}, # per-axis ramp width in pixels
    output_stack_mode="union",                    # canvas = union of all tile bboxes
    output_chunksize={"z": 64, "y": 512, "x": 512},
    output_zarr_url="fused_direct.zarr",
    zarr_options={"ome_zarr": True},
)
```

Note: per the source, `weights.get_blending_weights` accepts a `cupy=True` flag in v0.1.49+, enabling GPU computation of weights. `[CITED: github.com/multiview-stitcher/multiview-stitcher fusion.py — weights.get_blending_weights]`

### Pattern 3: Fallback — Hand-Rolled Weighted LSQ Position Solver

If multiview-stitcher's global solver is insufficient (e.g., handling of low-content edge pairs), port `stitch_global_grid_assignment.m`:

```python
# Source: PetaKit5D MATLAB stitch_global_grid_assignment.m, paraphrased to Python
# [CITED: github.com/abcucberkeley/PetaKit5D/blob/main/microscopeDataProcessing/stitch/]
import numpy as np
from scipy.sparse import csr_matrix, lil_matrix
from scipy.sparse.linalg import lsqr

def global_lsq_translations(pairwise_shifts, pairwise_quality, n_tiles, axes=("y", "x")):
    """
    For each axis independently:
      Variables: x_m for m=0..n-1 (one tile is anchor: x_0 := 0).
      Constraint for edge (i, j) with measured shift d_ij and weight w_ij:
          w_ij * (x_j - x_i) = w_ij * d_ij
      Solve weighted LSQ via scipy.sparse.linalg.lsqr.
    Returns: dict {axis: np.ndarray of length n_tiles}.
    """
    results = {}
    for ax_idx, ax in enumerate(axes):
        edges = [(i, j) for (i, j) in pairwise_shifts if pairwise_quality.get((i, j), 0) > 0]
        if not edges:
            results[ax] = np.zeros(n_tiles)
            continue
        A = lil_matrix((len(edges) + 1, n_tiles))
        b = np.zeros(len(edges) + 1)
        for k, (i, j) in enumerate(edges):
            w = float(pairwise_quality[(i, j)])
            A[k, i] = -w
            A[k, j] = +w
            b[k] = w * pairwise_shifts[(i, j)][ax_idx]
        A[-1, 0] = 1.0      # anchor: x_0 = 0
        b[-1] = 0.0
        x, _, _, _, _, _, _, _, _, _ = lsqr(csr_matrix(A), b)
        results[ax] = x
    return results
```

This is ~30 lines vs MATLAB's `lsqlin` call. The MATLAB version adds box constraints (`max_allow_shift`) which can be approximated by clipping the LSQ solution. `[CITED: PetaKit5D stitch_global_grid_assignment.m: "lsqlin(C,d,A,b)" — weighted constrained linear LSQ]`

### Pattern 4: Fallback — bwdist-based 3D Feather Weights

```python
# Source: PetaKit5D feather_blending_3d.m + compute_tile_bwdist.m, paraphrased
# [CITED: PetaKit5D/microscopeDataProcessing/stitch/]
import numpy as np
from scipy.ndimage import distance_transform_edt

def feather_weight_3d(tile_shape, overlap_widths):
    """
    Build a 3D weight volume that is 0 at the tile boundary along the
    overlap axes, ramps linearly inward, and saturates at the interior.
    Weight = min(distance_to_edge, overlap_width) / overlap_width.
    Equivalent to 1 - bwdist of a thin shell at the tile edge, normalised.
    """
    mask = np.ones(tile_shape, dtype=bool)
    # Zero out a 1-pixel ring along Y and X (no feather along Z for this dataset)
    mask[:, 0, :] = mask[:, -1, :] = False
    mask[:, :, 0] = mask[:, :, -1] = False
    dist = distance_transform_edt(mask)
    ow = max(overlap_widths.get("y", 144), overlap_widths.get("x", 144))
    w = np.clip(dist / ow, 0.0, 1.0).astype(np.float32)
    return w

# Stitching loop (per Z-slab, replaces place_tile_slab):
canvas = np.zeros((nz, H, W), dtype=np.float32)
w_canvas = np.zeros_like(canvas)
for m in range(n_tiles):
    fused_slab = ...           # (nz, 1920, 1920) uint16 from fuse_sides
    w_tile = feather_weight_3d(fused_slab.shape, {"y": 144, "x": 144})
    y0, y1 = registered_pos[m]["y"], registered_pos[m]["y"] + 1920
    x0, x1 = registered_pos[m]["x"], registered_pos[m]["x"] + 1920
    canvas[:, y0:y1, x0:x1]    += fused_slab.astype(np.float32) * w_tile
    w_canvas[:, y0:y1, x0:x1]  += w_tile
fused = (canvas / np.maximum(w_canvas, 1e-8)).clip(0, 65535).astype(np.uint16)
```

Critically, this replaces the current code's 2-D **separable cosine taper** with a true 2-D (or 3-D) **distance-transform** weight, which sums to a smooth surface even at 3- and 4-tile corner junctions. `[CITED: PetaKit5D feather_blending_3d.m: "tim_block = sum(tim_f_block .* tim_w_block, 4) ./ sum(tim_w_block, 4)" — weighted average over the 4-th (tile) axis, exactly the formula above]`

### Anti-Patterns to Avoid

- **Modifying `fuse_sides`, `_gaussian_ramp`, or `read_tile_zchunk`.** Phase 2.5 must not touch these — STITCH-06 requires `git diff` to show zero changes to those line ranges in `07_direct_fuse.py`.
- **Materialising 30 intermediate per-tile zarrs to disk.** Each tile is 1920×1920×1557 uint16 = 11 GB. 30 tiles × 2 channels = 660 GB of intermediates. Read tiles JIT from the CZI in each Stage 2 task instead (same pattern as Phase 2).
- **Running `multiview-stitcher` on the full 1557-plane volume in one process.** The canvas alone is 168 GB float32; per-Z-slab chunking is mandatory. Use `output_chunksize` matching the existing zarr chunks `(64, 512, 512)`.
- **Re-registering inside Stage 2.** Stage 1 produces the final transforms once; Stage 2 only blends.
- **Installing multiview-stitcher into `lightsheet_env`.** Its dependency `dask<2025.11.0` conflicts with `lightsheet_env`'s `dask 2026.3.0`. Use a separate `mvstitch_env`.
- **Per-Z-plane independent blending in 2D.** Mid-Z artefacts in Phase 2 are partly because weights are 2D-only; a 3D feather (or per-Z 2D feather computed from the same XY mask shared across Z) avoids inconsistencies.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Pairwise phase correlation with sub-pixel | scikit-image `phase_cross_correlation` from scratch with FFT plumbing | `multiview_stitcher.registration.phase_correlation_registration` | Already wraps skimage's PCC with multi-shift disambiguation and SSIM validation. `[CITED: registration.py — "phase correlation registration using a modified version of skimage's phase_cross_correlation"]` |
| Weighted LSQ over translation graph | Hand-rolled normal-equations + dense `np.linalg.lstsq` | `multiview_stitcher.param_resolution.groupwise_resolution(..., method="global_optimization")` OR fallback `scipy.sparse.linalg.lsqr` on a sparse incidence matrix | sklearn/scipy LSQ are battle-tested; sparse form scales to many tiles. Network-x for graph topology. |
| 3-D distance-transform feather weights | Pixel-by-pixel ramp code | `scipy.ndimage.distance_transform_edt` on the tile interior mask | EDT is C-implemented and exact; no risk of corner-case bugs at 3-/4-tile junctions |
| Multi-tile weighted-average canvas accumulation | Float32 canvas + weight canvas + post-divide loop | `multiview_stitcher.fusion.weighted_average_fusion` (default `fusion_func`) | Handles arbitrary-tile overlaps, dask-parallel, zarr-native; existing code does it but in a 2-D-only way |
| OME-Zarr writer (with multiscale pyramid) | tifffile/zarr stitching by hand | `multiview-stitcher` `output_zarr_url=...` + `zarr_options={"ome_zarr": True}` (uses ngff-zarr under the hood) | Single-call API; matches Phase 3 expectations |
| Z-slab partition arithmetic for SLURM array | Custom partition logic | Reuse Phase 2's `Z_STARTS=(0 256 ... 1408)` bash arrays | Already proven, chunk-aligned |
| Tile bbox + canvas geometry tracking | New bookkeeping classes | `spatial_image.SpatialImage` (xarray.DataArray with translation/scale attrs) | Handles transforms, unions, intersections natively |

**Key insight:** The only code we should write from scratch is (a) the glue that calls `multiview-stitcher` with the right inputs, (b) the Stage 1/2 SLURM scripts, (c) the diagnostics JSON serialiser, and (d) the notebook cell. Everything algorithmic comes from the library.

## Common Pitfalls

### Pitfall 1: dask version conflict between multiview-stitcher and lightsheet_env
**What goes wrong:** `pip install multiview-stitcher` into `lightsheet_env` downgrades `dask` from 2026.3.0 to 2025.10.x, breaking other parts of the project that depend on the newer dask.
**Why it happens:** multiview-stitcher 0.1.52 pins `dask <2025.11.0` due to API changes in dask's task-graph API.
**How to avoid:** Create a separate `mvstitch_env`. Stage 1 and Stage 2 run in `mvstitch_env`; they import or shell out to read tile data (read_tile_zchunk, fuse_sides) — easiest is to install `aicspylibczi`, `cupy-cuda12x`, and `cucim` (optional) into `mvstitch_env` and copy/import `fuse_sides` into `08_stitch.py`. `fuse_sides` has no dask dependency so it runs in either env.
**Warning signs:** `pip install multiview-stitcher` warnings about dask conflict; later, dask scheduler errors at job runtime. `[VERIFIED: pip index versions multiview-stitcher 0.1.52 + pyproject.toml dask pin]`

### Pitfall 2: Re-introducing the cosine-taper bug via wrong blending_widths
**What goes wrong:** Setting `blending_widths` too narrow (e.g., 32 px on a 288-px overlap) leaves a hard seam at the centre of the overlap region. Setting it too wide (e.g., 1000 px on a 1920-px tile) over-attenuates tile interiors.
**Why it happens:** Easy to misinterpret what `blending_widths` controls.
**How to avoid:** Set `blending_widths` to approximately HALF the tile-overlap in pixels. KL018: stage step = 1632 px between adjacent tile origins, tile size = 1920 px → overlap = 288 px → `blending_widths = {"y": 144, "x": 144}`. Verify via the notebook seam-quality cell after a substack run.
**Warning signs:** Notebook seam-NCC < 0.85 at tile junctions; mid-Z mosaic shows a dark/bright line at the centre of each overlap.

### Pitfall 3: registration.register() picks wrong scale level on multiscale-spatial-images
**What goes wrong:** Default `reg_res_level` may be coarser than needed for KL018's 0.915-µm XY; pairwise shifts come back quantised to >5 px, missing the seam.
**Why it happens:** `multiscale_spatial_image` builds a pyramid; `reg_res_level=None` lets the lib pick.
**How to avoid:** Explicitly set `reg_res_level=0` (full resolution) for the first run; bump to 1 only if Stage 1 takes longer than 20 min. Set `registration_binning={"z": 1, "y": 1, "x": 1}` (no binning) since KL018 tiles are only 1920×1920 — small enough.
**Warning signs:** Stage 1 finishes in seconds (suspiciously fast) or pairwise shifts in `stitch_diagnostics.json` are all multiples of 2 or 4.

### Pitfall 4: Anisotropic voxels confuse the global solver
**What goes wrong:** KL018 voxel: z=3.515 µm, y=x=0.915 µm (anisotropy ratio 3.84). If we pass per-pixel shifts to a solver that's working in µm, or vice versa, Z drift gets scaled wrong.
**Why it happens:** `multiview-stitcher` works in physical units (µm) once `scale` is set on the spatial_image. Translations must be in the same units.
**How to avoid:** Set `scale={"z": 3.515, "y": 0.915, "x": 0.915}` and `translation` in **µm**, not pixels: `translation={"y": pos_y_px * 0.915, "x": pos_x_px * 0.915}`. After registration, convert the resulting transform back to pixels for the output zarr.
**Warning signs:** Apparent Y drift of ~3.84× the actual misalignment.

### Pitfall 5: Mid-Z-only reference slab repeats the Phase 2 bug
**What goes wrong:** Reading just the mid-Z slab (e.g., Z=778) for register() reproduces the existing bug — tiles that are background at Z=778 have no signal to correlate.
**Why it happens:** Stage 1 needs SOME tile content; using only one Z plane is fragile.
**How to avoid:** Read a Z-slab of ~32-64 planes around mid-Z (e.g., Z=750:810) and let `phase_correlation_registration` correlate in 3D. This matches PetaKit5D's `cross_correlation_registration_3d` approach. `[CITED: PetaKit5D cross_correlation_registration_3d.m]`
**Warning signs:** Some pairs in diagnostics JSON have `quality < 0.1` despite being in the tissue interior.

### Pitfall 6: Output zarr canvas grows unbounded after registration
**What goes wrong:** If a few tile pairs converge to wildly wrong shifts, the global LSQ accepts them and the canvas extent balloons to e.g., 30000×20000.
**Why it happens:** No bounds on the solver.
**How to avoid:** Set `post_registration_do_quality_filter=True, post_registration_quality_threshold=0.2` in `register()`. Also clip the resulting translations to `|delta| < 50 px` from initial stage positions before fusing. Verify `output_stack_properties` is within sane bounds (8585±200, 10095±200 pixels) BEFORE allocating Stage 2 zarr.
**Warning signs:** Stage 1 logs "canvas H=20000" or similar; Stage 2 zarr allocation fails with memory error.

### Pitfall 7: Stage 1 GPU dependency not really required
**What goes wrong:** Allocating a GPU for Stage 1 (which is mostly NumPy/scipy registration) wastes scheduling time.
**Why it happens:** Reusing the Stage 1 NCC script from Phase 2 by mistake.
**How to avoid:** Stage 1 needs GPU **only** to run `fuse_sides` on tile reference slabs (15 sec each × 30 tiles = ~8 min). It does NOT need GPU for `register()` itself. Run on a regular CPU partition if reference-slab fusion is precomputed; otherwise use the smallest GPU available (A30 with `--time=00:30:00`).
**Warning signs:** Stage 1 sits in gpuq queue for hours waiting for an A30 while CPU partition is empty.

### Full `08_stitch.py` skeleton (verified pattern)

```python
"""
08_stitch.py — Globally-optimised stitching for KL018 (Phase 2.5).
Reads CZI dual-side data via the unchanged 07_direct_fuse.fuse_sides path,
registers tiles with multiview-stitcher's pairwise+global pipeline, and
fuses with weighted-average + blending_widths feathering.

Stage 1: --stage register   → writes stitch_positions.json + stitch_diagnostics.json
Stage 2: --stage blend --z-start N --z-end M → fuses a Z-slab into pre-allocated zarr
"""
import argparse, json, sys
from pathlib import Path
import numpy as np
import zarr

# Import the unchanged fusion path. fuse_sides + read_tile_zchunk live in
# 07_direct_fuse.py and are NOT modified by this phase (STITCH-06).
sys.path.insert(0, str(Path(__file__).parent))
from importlib import import_module
_direct = import_module("07_direct_fuse")
read_tile_zchunk = _direct.read_tile_zchunk
fuse_sides = _direct.fuse_sides
get_czi_layout = _direct.get_czi_layout

from aicspylibczi import CziFile
from multiview_stitcher import registration, fusion, msi_utils
from multiview_stitcher import spatial_image_utils as si_utils


def build_tile_sims(czi, layout, z_slab_start, z_slab_end, c=0,
                    initial_positions=None):
    """For each of n_tiles M, read [z_slab_start, z_slab_end), fuse dual-side
    illumination, wrap as a spatial_image with stage_metadata translation in µm."""
    voxel = layout["voxel_size_um"]  # {"x": 0.915, "y": 0.915, "z": 3.515}
    sx, sy, sz = voxel["x"], voxel["y"], voxel["z"]
    sims = []
    for m in range(layout["n_tiles"]):
        if layout["dual"]:
            sa = read_tile_zchunk(czi, m, 0, c, 0, z_slab_start, z_slab_end,
                                  layout["tile_h"], layout["tile_w"], 4)
            sb = read_tile_zchunk(czi, m, 1, c, 0, z_slab_start, z_slab_end,
                                  layout["tile_h"], layout["tile_w"], 4)
            fused = fuse_sides(sa, sb, axis=2, sigma_frac=0.9)  # validated params
        else:
            fused = read_tile_zchunk(czi, m, 0, c, 0, z_slab_start, z_slab_end,
                                     layout["tile_h"], layout["tile_w"], 4)
        bb = (initial_positions or layout["tile_bboxes"])[m]
        tx = bb["x"] if isinstance(bb, dict) else bb.x
        ty = bb["y"] if isinstance(bb, dict) else bb.y
        sim = si_utils.get_sim_from_array(
            fused,
            dims=("z", "y", "x"),
            scale={"z": sz, "y": sy, "x": sx},
            translation={"z": 0.0, "y": ty * sy, "x": tx * sx},
            transform_key="stage_metadata",
        )
        sims.append(sim)
    return sims


def stage_register(args, czi, layout):
    """Register all tiles using a Z-slab around mid-Z. Write transforms+diagnostics."""
    n_z = layout["n_z"]
    z_mid = n_z // 2
    z0 = max(0, z_mid - 32)
    z1 = min(n_z, z_mid + 32)
    print(f"Registering using Z-slab {z0}:{z1} (mid={z_mid})")
    sims = build_tile_sims(czi, layout, z0, z1, c=0)
    msims = [msi_utils.get_msim_from_sim(sim) for sim in sims]
    params = registration.register(
        msims,
        reg_channel_index=0,
        transform_key="stage_metadata",
        new_transform_key="registered",
        pairwise_reg_func=registration.phase_correlation_registration,
        groupwise_resolution_method="global_optimization",
        post_registration_do_quality_filter=True,
        post_registration_quality_threshold=0.2,
        return_dict=True,
    )
    # Persist transforms
    out = Path(args.out_dir)
    positions = {}
    for m, p in params["params"].items():
        # p is an xarray.DataArray (affine matrix); extract translation
        positions[m] = {
            "translation_um": _extract_translation_um(p),
            "translation_px": _to_pixels(_extract_translation_um(p), layout),
        }
    json.dump(positions, open(out / "stitch_positions.json", "w"), indent=2)
    diagnostics = {
        "pairwise": _flatten_pairwise(params["pairwise_registration_results"]),
        "groupwise": _flatten_groupwise(params["groupwise_resolution_info"]),
        "z_slab_used": [z0, z1],
        "n_tiles": layout["n_tiles"],
        "voxel_size_um": layout["voxel_size_um"],
        "library_version": "multiview-stitcher==0.1.52",
    }
    json.dump(diagnostics, open(out / "stitch_diagnostics.json", "w"), indent=2)
    print(f"Wrote stitch_positions.json + stitch_diagnostics.json")


def stage_blend(args, czi, layout):
    """Blend a Z-slab into pre-allocated fused_direct.zarr."""
    pos = json.load(open(Path(args.out_dir) / "stitch_positions.json"))
    out_z = zarr.open(args.out_zarr, mode="r+")
    z0, z1 = args.z_start, args.z_end
    for t in range(layout["n_t"]):
        for c in range(layout["n_c"]):
            for chunk_z0 in range(z0, z1, args.z_chunk):
                chunk_z1 = min(chunk_z0 + args.z_chunk, z1)
                sims = build_tile_sims(czi, layout, chunk_z0, chunk_z1, c=c,
                                        initial_positions=_pos_to_bboxes(pos, layout))
                # Reattach the "registered" transform from stitch_positions.json
                for m, sim in enumerate(sims):
                    si_utils.set_sim_affine(sim, _build_affine(pos[str(m)]),
                                            transform_key="registered")
                fused = fusion.fuse(
                    sims=sims,
                    transform_key="registered",
                    fusion_func=fusion.weighted_average_fusion,
                    blending_widths={"z": 0, "y": 144, "x": 144},
                    output_stack_mode="union",
                    output_chunksize={"z": chunk_z1 - chunk_z0, "y": 512, "x": 512},
                )
                # Materialise the dask result and write to the pre-allocated zarr
                arr = fused.compute().astype(np.uint16)
                out_z[t, c, chunk_z0:chunk_z1] = arr


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--stage", choices=["register", "blend"], required=True)
    ap.add_argument("--czi", required=True)
    ap.add_argument("--out-dir", required=True)
    ap.add_argument("--out-zarr", required=True)
    ap.add_argument("--z-start", type=int, default=0)
    ap.add_argument("--z-end", type=int, default=None)
    ap.add_argument("--z-chunk", type=int, default=64)
    args = ap.parse_args()
    czi = CziFile(args.czi)
    cache = Path(args.out_dir) / "czi_layout_cache.json"
    layout = get_czi_layout(czi, cache_path=cache)
    if args.stage == "register":
        stage_register(args, czi, layout)
    else:
        if args.z_end is None: args.z_end = layout["n_z"]
        stage_blend(args, czi, layout)


if __name__ == "__main__":
    main()
```

## Open Questions

1. **Should Stage 1 use `reg_res_level=0` (full res) or `reg_res_level=1` (2× downsampled)?**
   - What we know: KL018 tiles are 1920×1920 — small enough for full-res registration. PetaKit5D's `cross_correlation_registration_3d.m` uses `max_pooling_3d` downsampling for speed.
   - What's unclear: Whether registration at full res produces materially better positions than 2× downsampled.
   - Recommendation: Start with `reg_res_level=0` for the first substack validation; if Stage 1 wall time > 20 min, switch to `reg_res_level=1`.

2. **Should `blending_widths` include `z`?**
   - What we know: KL018 has no Z-direction tile mosaicking — all 30 tiles span the full Z range. Therefore no Z-axis tile boundaries exist to feather across.
   - Recommendation: `blending_widths={"z": 0, "y": 144, "x": 144}`. Confirm in notebook output that no Z-attenuation appears.

3. **Should `compute_overlap_norm_scales` (per-tile intensity scaling) still be applied?**
   - What we know: Phase 2 used it because cosine-taper feathering didn't normalise out per-tile illumination differences fully.
   - What's unclear: Whether proper N-D feather blending makes it unnecessary OR whether tiles genuinely have different mean intensities.
   - Recommendation: Run substack with normalisation OFF first; if illumination uniformity ratio > 1.15, enable it.

4. **Will the canvas shape change vs (8585, 10095)?**
   - What we know: Global LSQ may pull tile positions differently from the current MST-from-tile-0; if the solver consistently shifts everything by the same amount the canvas only translates, but if it tightens/loosens the mosaic, dimensions change.
   - Recommendation: Stage 1 computes the new canvas dims from registered positions and recreates `fused_direct.zarr` accordingly. Downstream Phase 3 (OME-TIFF export) should NOT hard-code (8585, 10095).

5. **Is there a Phase 2-existing fused_direct.zarr that should be preserved?**
   - What we know: The current `fused_direct.zarr` is the Phase 2 output — the one we are replacing.
   - Recommendation: Back up `fused_direct.zarr` → `fused_direct_phase2.zarr` before Stage 1 of Phase 2.5 starts, so visual comparison is possible.
